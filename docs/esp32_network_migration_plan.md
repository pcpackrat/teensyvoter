# ESP32/WT32-ETH01 Full Network Migration for TeensyVoter

## Context

Currently the Teensy 4.1 does its own Ethernet (`NativeEthernet`/FNET) as the primary network path, with a plain ESP32 devkit (`esp32_firmware/Spirit/`) as a WiFi-fallback co-processor bridged over SPI, and the Teensy hosts its own web config UI (`TeensyWebServer.cpp`) directly on its Ethernet hardware. The goal is to offload all non-audio work (networking, web config) from the Teensy's timing-sensitive main loop: swap the ESP32 for a **WT32-ETH01** (ESP32 + integrated LAN8720 Ethernet), make it the **sole** network interface and **sole** web-config host, and remove the Teensy's own Ethernet and web server entirely. The Teensy talks to the ESP32 purely over SPI; the ESP32 owns all of L3.

This reverses the direction stated in `docs/reverse_tunnel_plan.md` (committed the day before), which called for *removing* the ESP32 path. That doc's Context section (line 12) and Staging step 0 (line 77) are now stale and need a follow-up correction — out of scope to edit as part of this plan, flagged for later. If/when that tunnel work resumes, its dial-out relay client should target the ESP32/WT32-ETH01 (full lwIP stack, more RAM/flash, existing WireGuard-ESP32-Arduino ports to reference) rather than the from-scratch Teensy/FNET Monocypher port originally scoped — a side-benefit of this migration, not designed in detail here.

**Scope decision**: this stays in the current repo/folder, not a fork into a new project. The parts of this codebase that are hard-won and correctness-critical — GPS dead-reckoning timestamps, the DSP/resampling chain, the Voter Protocol auth state machine (just fixed a real bug in it this session) — are untouched by this migration; only the network/web layers change. The "build it right this time" instinct applies specifically to the SPI wire protocol (rebuilt from scratch in Phase 0, not patched) and the now-vestigial dual-driver `NetworkDriver` abstraction (deleted outright in Phase 4, not kept around) — both get a clean redo without needing to discard the rest of a working, field-validated codebase. Staged, gated phases plus git history are the safety net in place of a clean-slate fork.

**Explicitly accepted risk**: `docs/troubleshooting_next_steps.md` (2026-01-12) documents that audio traffic over the existing SPI/WiFi-fallback bridge achieved only ~20pps against a 50pps (20ms cadence) target — ~60% effective loss, with no later doc/changelog confirming resolution. Root cause by direct code inspection: every SPI send is a blocking, unpipelined, always-512-byte transaction (~3.1ms+ minimum overhead per call) with no prioritization between audio, GPS keepalive, syslog, and config traffic — easily exceeds the 20ms audio budget when multiple sends land in the same loop pass. The user was shown this and chose to proceed with full commit (all traffic via ESP32/SPI, not a hybrid keeping audio on Teensy Ethernet). **Fixing and proving this transport is therefore a hard, gating prerequisite (Phase 0) — do not proceed to hardware bring-up until it passes a measured bar.**

Two distinct update paths, both requiring zero physical touch at the ESP32: **(1)** routine field updates via Phase 2's OTA-over-SPI push (works over the already-connected SPI link, no PC needed on-site at all) and **(2)** first-flash/factory/recovery via the EN+GPIO0+UART0 passthrough described in Phase 1 below (needs a PC on the Teensy's USB, but nothing touches the ESP32 module directly — the Teensy acts as the USB-serial+auto-reset adapter the WT32-ETH01 doesn't have onboard).

**What flows over SPI, after migration:**
- Teensy -> ESP32: outbound UDP (audio, GPS keepalive, syslog), full config push on ESP32 boot/reconnect, **[new]** firmware blob chunks.
- ESP32 -> Teensy: inbound UDP (voter protocol control/audio), config-write commands from the web UI (`CFG_CMD_SET_PARAM`), DNS results, link/IP status, **[new]** current firmware version on request.

**Config: one settings table, two edit surfaces, both relay to the same place.** Every setting (network, voter protocol, radio/DSP, syslog) still lives in `SysConfig`/EEPROM on the Teensy — nothing moves. What changes is *where you can edit it*: the ESP32 web UI (now the only network-facing UI) and the Teensy's serial CLI (kept fully writable, per your call — useful for bench work with no network/ESP32 involved at all) are two front ends to the exact same underlying struct, exactly like `/wifi` and `/voter` already work today. No dual-source-of-truth risk since there's still only one writer of record (the Teensy applying either a serial-CLI edit or a relayed `CFG_CMD_SET_PARAM`). WiFi SSID/password fields go away entirely — nothing to edit from either surface once WiFi is never used.

## Ground-truth facts confirmed this session

- `include/SpiProtocol.h`: `MAX_SPI_BUF 512`, every transaction is a fixed 512-byte block transfer regardless of payload. `PARAM_*` enum has 24 IDs; `PARAM_HOST_PWD 0x05` already exists. **Missing** vs. full `SysConfig` (`include/ConfigManager.h:20-64`, 36 fields): `staticIP`, `subnetMask`, `gateway`, `staticDNS`, `dnsServerIP`, `useStaticIP`, `mac[6]`, `timingOffsetMs` — 8 fields, next free ID `0x24`.
- `esp32_firmware/Spirit/src/Spirit.cpp:19-59` `SysConfigMirror` is **already** a byte-for-byte match of `SysConfig`, including all 8 "missing" fields above — confirmed by direct read. The gap is only in the `PARAM_*` dispatch/enum, not the mirror struct. No `SysConfigMirror` changes needed in Phase 2.
- `src/EspSpiDriver.cpp:37-76` `sendPacketTo()`: opportunistic `parsePacket()` if READY is HIGH (a second full transaction) → `delayMicroseconds(2000)` fixed pad → `SPI.beginTransaction()` at 4MHz (comment: "maximum stable speed for long-wire SPI slave") → `delayMicroseconds(100)` pad → always transfers the full 512 bytes via `SPI.transfer(buffer, MAX_SPI_BUF)`. Minimum ~3.1ms per call, blocking the Teensy's single main loop thread every time — audio, GPS keepalive (500ms), syslog, and config-polling all serialize through this one channel with no pipelining (`queue_size=3` configured in `Spirit.cpp:220` but unused beyond driver internals — one transaction at a time).
- `include/VoterProtocol.h:35-39` `PROXY_AUDIO_PACKET` = 185 bytes; plus 9-byte `CMD_SEND_UDP` header = 194 bytes actually needed vs. 512 always transferred.
- `src/Logger.cpp:96-103`: `Logger::update()` drains its *entire* pending queue in one call with `delay(50)` between entries if more than one is pending — a second blocking-multiple-sends-per-call hazard compounding the SPI problem, worth fixing alongside it.
- `esp32_firmware/Spirit/src/Spirit.cpp:9-13` current SPI pins (devkit): MOSI=23, MISO=19, SCLK=18, CS=5, READY=22. Teensy-side (`src/main.cpp:123`): CS=26, Ready=24, Reset=25 (unaffected by the ESP32 board swap).
- Root `platformio.ini` `[env:esp32]` and `esp32_firmware/Spirit/platformio.ini` `[env:esp32dev]` both hardcode `board = esp32dev` — both need updating.
- WT32-ETH01: fixed/reserved EMAC pins GPIO 0,16,18,19,21,22,23,25,26,27 (clock, power, MDC/MDIO, TX/RX data+control). Free VSPI defaults: SCK=12, MISO=15, MOSI=14. IO32/33 are general-purpose bidirectional (default I2C, unused here). **IO35/IO39 are input-only** — usable only for signals the ESP32 *receives* (CS, RESET), never for READY (which the ESP32 must drive as output). No boot/reset button — GPIO0 is claimed by the ETH clock, so the usual auto-reset-into-bootloader flashing trick doesn't apply; flashing needs external hardware (jumper/switch) to pull GPIO0 low.
- PlatformIO has native `board = wt32-eth01` support; arduino-esp32 core has native `ETH.h` for this board's LAN8720, no extra lib needed. `WiFiUDP` is IP-layer and should work transparently over `ETH` — confirm during implementation, not file-verified.

## Phase 0 — SPI Transport Reliability Fix (gating; current hardware, no board swap yet)

**Status: implemented, awaiting hardware soak test.** This is a protocol/timing problem, not a PHY problem — fixed and measured on the existing devkit ESP32, no WT32-ETH01 needed.

**0.1 Instrumentation** (implemented): `VoterClient::processAudioFrame()` (`VoterClient.cpp`) times every audio `sendPacket()` call with `micros()` and `VoterClient::_reportSpiStats()` prints a `[SPI-STATS]` line every 5s — window length, send count, achieved pps, avg/max latency, count of sends over 15ms. `Spirit.cpp`'s existing 5s heartbeat now also reports `Txns:` (completed SPI transactions) and `UDPfwd:` (UDP packets relayed) per window. Cross-check against `tools/measure_pps.py` on the Asterisk server side as independent ground truth.

**0.2 Architectural fixes (implemented)**:
1. **Right-size transfers** — `EspSpiDriver::sendPacketTo()` now sends only `9 + payloadLen` bytes (a ~194-byte audio frame vs. the old fixed 512) *unless* the ESP32's READY line is already high when the send starts, in which case it falls back to the full `MAX_SPI_BUF` transfer in the same transaction rather than truncating whatever the ESP32 has queued. Cuts the common-case audio transfer from ~1024µs to ~388µs at 4MHz with no added risk to full-duplex correctness.
2. **Reduced the `delayMicroseconds(2000)` pad to 200µs** (`EspSpiDriver.cpp`) — not eliminated outright since this hasn't been bench-verified; if communication is flaky after flashing, this is the first constant to tune back up.
3. **Collision-evasion removed from the audio hot path** — folded into the right-sizing fix above (item 1) rather than kept as a separate opportunistic `parsePacket()` transaction; there is no longer a second SPI transaction on the send path at all.
4. **Real pipelining on the ESP32** — `Spirit.cpp` now keeps a transaction perpetually queued via `spi_slave_queue_trans()`/`spi_slave_get_trans_result()` (non-blocking poll) instead of blocking on `spi_slave_transmit()` once per loop iteration, so the slave is always armed the instant the Teensy clocks a transaction. This required a correctness fix alongside it: `queueConfigCmd()` (used by the web UI's config-write path) used to write straight into `sendbuf`, which was only safe because the old loop was fully blocking; it now stages into a separate buffer (`cfgCmdStaged`) and only gets copied into `sendbuf` in the one safe window right after a transaction completes and before the next is queued.
5. **Priority — addressed structurally, not with an explicit scheduler.** Given item 6 (Logger) bounds every non-audio send to at most one right-sized SPI transaction per call, and general right-sizing (item 1) shrinks every transaction's worst-case blocking time, the original plan's more elaborate "check time-budget-remaining and defer" scheduler was skipped as premature complexity — worth revisiting only if the soak test below shows this isn't sufficient.
6. **`Logger::update()` bounded to one send per call** (`Logger.cpp`) — no longer drains its whole queue with a 50ms delay between entries; a backlog now drains one entry per loop iteration instead of stalling the loop for 100ms+ in a single call.

**0.3 Measurement and pass bar**: hold PTT/COS active continuously for 5 minutes, watch the Teensy's `[SPI-STATS]` serial output and the ESP32's heartbeat `Txns:`/`UDPfwd:` counts, and run `tools/measure_pps.py` server-side as independent ground truth. **Pass bar: sustained ≥98% of 50pps over rolling 10s windows for the full 5 minutes, zero windows below 40pps, max single-frame send latency <15ms for ≥99.5% of frames** (the `[SPI-STATS]` `over15ms` counter should stay at/near 0). Do not proceed to Phase 1 until this is met.

**First two hardware runs (2026-07-12, ~45-65s each, Ethernet disconnected to force the ESP32/SPI path)**: the transport fix itself worked cleanly both times — `avgPps=50.0` sustained across every full 5s window (9 windows the first run, 13 the second), latency ~715-716µs average, max ~717-798µs, `over15ms=0` throughout — a clean hit against the ~20pps/60%-loss baseline. Both runs ended with `SPI Slave Started` reappearing (a fresh ESP32 boot) and a `rst:0x1 (POWERON_RESET)` banner; initially read as a watchdog-starvation crash (see below), but this was the user manually restarting the boards between test segments, not a firmware fault — confirmed no code path re-triggers the ESP32's reset pin at runtime (`spiDriver.begin()`, which drives it, is only ever called once in `setup()`). Neither run is a real pass/fail yet since neither was an uninterrupted full 5 minutes.

While investigating the (ultimately non-)crash, found and fixed a real latent issue anyway: `spi_slave_get_trans_result(RCV_HOST, &doneTrans, 0)` — a true 0-tick poll — never yields to the RTOS scheduler when nothing is ready, which could starve the ESP32's task watchdog under sustained load even though it isn't what happened here. The old blocking `spi_slave_transmit()` avoided this incidentally by blocking (and therefore yielding). **Fixed**: changed the timeout to `pdMS_TO_TICKS(1)` (1 tick, not 0). Worth keeping regardless of the false alarm.

**EMI regression found — not yet resolved (2026-07-12)**: after flashing the above, the user reported audible buzzing on this unit's radio audio, absent on the other (unmodified) VOTER clients — isolated by testing Ethernet vs. the ESP32/SPI path: silent on Ethernet, buzzing on ESP32/SPI.

First attempt (did not fix it): widened the `spi_slave_get_trans_result` poll ceiling from 1 tick to `pdMS_TO_TICKS(8)`, on the theory that ~1000Hz idle-loop GPIO/SPI-bus churn (vs. ~20Hz with the old blocking `spi_slave_transmit()`) was coupling into the audio path. Buzz persisted unchanged after this fix, ruling out idle-loop/SPI-GPIO switching rate as the cause.

**Correction**: user confirmed WiFi/the SPI fallback path had run fine (no buzz) before this session's work — so the "latent hardware property, just never exercised" framing above was wrong. This is something these changes actually introduced.

Better-fitting hypothesis: before Phase 0, the SPI/WiFi path only achieved ~20pps with heavy loss and irregular timing. Phase 0 made it hit a rock-solid, perfectly periodic 50 transactions/sec — one SPI-relayed WiFi UDP transmission every 20ms, no exceptions. A perfectly periodic ~50Hz digital/RF switching event is a classic, highly audible EMI signature (mains-hum-adjacent territory) in a way irregular/lossy traffic never was. The fix likely didn't add more total interference so much as make existing interference perfectly regular and therefore tonal/audible.

Second attempt (made it worse, reverted): tried `WiFi.setTxPower(WIFI_POWER_8_5dBm)` (down from default ~19.5dBm max) in `setup()`, on the theory that less RF power couples less. **Buzz got louder**, not quieter. Likely explanation: lower power pushed the WiFi link into a worse-quality regime (more retries, slower/more robust modulation, longer airtime per packet to move the same data) — more total RF burst duration, not less. This is still a useful result: it confirms WiFi TX activity (specifically, the once-per-20ms UDP relay burst) is implicated, just not in the naively-expected direction. Reverted to stock/default TX power; do not re-attempt without an actual link-quality read (RSSI, retry counts) to know which direction genuinely helps.

**Correction #2**: user identified this as a timing issue, not RF — correct call. Root cause found: `VoterClient::processAudioFrame()` (`src/VoterClient.cpp`) is called from *inside* the record-queue-draining `while` loop in `src/main.cpp` (~line 1730), and its ~715µs blocking SPI send used to happen synchronously right there, mid-drain. That's not a WiFi/RF question at all — it's the Teensy's own audio-buffer-draining cadence for that loop pass getting perturbed by a blocking I/O call sitting in the middle of it, once every 20ms, with perfect regularity for the first time thanks to Phase 0 actually working. Explains everything: silent on Ethernet (`EthernetDriver::sendPacket()` is a fast direct hardware call, not a ~715µs blocked transfer), buzzes on SPI, present "constant" per the user's report (ties to frame cadence, not to whether WiFi is idle), and the two WiFi-TX-power experiments were both irrelevant red herrings.

**Fix implemented**: deferred the actual send out of the audio-processing critical path. `processAudioFrame()` now stages the built packet into `_pendingAudioPkt`/`_pendingAudioSend` (`include/VoterClient.h`, `src/VoterClient.cpp`) instead of sending immediately; a new `VoterClient::flushPendingAudio()` does the real `_net->sendPacket()` call, and is invoked from `main.cpp` right after the record-queue `while` loop closes (~line 1979) instead of from inside it. Guarded against the rare case of two frames completing within the same drain pass (possible via the resample-carry remainder) — `processAudioFrame()` flushes any already-pending frame immediately before staging a new one, so nothing is silently dropped/overwritten. Both `pio run -e teensy41` and `-e esp32` (unaffected, Teensy-only change) build clean. Not yet flashed/tested for the buzz.

**Retest result**: buzz "lighter, not gone" after the deferred-send fix — confirms mid-drain scheduling was A contributor, but not the whole story. A partial improvement from a scheduling fix, with a residual left over, points at an electrical/EMI component that no amount of software scheduling can address: the SPI clock/data lines themselves toggling at 4MHz for ~400-700µs every 20ms, with perfect regularity, likely coupling via ground bounce/power-rail noise/trace crosstalk near the SGTL5000 — independent of *when* in the loop the transfer happens.

**Third attempt (awaiting test result)**: dropped the SPI clock from 4MHz to 2MHz in both `sendPacketTo()` and `parsePacket()` (`src/EspSpiDriver.cpp`) — slower edges generally couple less into nearby analog circuitry, and there's enormous time budget to spare (~715µs of a 20ms window). **Caveat**: an older, now-superseded version of this driver documented 2MHz as "broken" (`docs/troubleshooting_next_steps.md`), predating this session's queue-based ESP32 pipelining and right-sized transfers — may not still apply, but watch the SPI-STATS/heartbeat counters for new loss/timeout symptoms, not just listen for buzz, in case the old issue resurfaces. Revert to 4000000 in both spots if so. Builds clean, not yet flashed/tested.

**Retest result**: 2MHz clock made no meaningful difference either. Four attempts now (idle-loop rate, WiFi TX power, mid-drain scheduling, clock speed) — only the scheduling one had any effect, and only partial. User correctly pushed back on the "must be wiring/EMI" framing: the Ethernet-vs-SPI comparison doesn't actually distinguish wiring/EMI from other SPI-mode-only causes, since WiFi radio activity, SPI electrical activity, *and* the Teensy's own CPU-blocking-during-transfer are all simultaneously absent on Ethernet and present on SPI — that test alone can't tell them apart.

**Root cause, found**: re-examined what actually differs across all four results and it converges on one thing — `sendPacketTo()` was a fully blocking `SPI.transfer()`, holding the Teensy's CPU in a busy-wait for the entire transfer (~700µs+) with perfect 20ms regularity for the first time (Phase 0 finally made this reliable). This explains every result: idle-poll-rate/clock-speed changes don't touch the fact that the CPU is blocked solid, so no effect; deferring past the drain loop changed *when* the block happens relative to other audio-pipeline work, so partial effect; lower WiFi TX power caused more ESP32-side retries, occasionally lengthening how long the Teensy's transfer takes to complete, so worse effect. It was never about RF or EMI — it's the Teensy's own CPU being unavailable to service its real-time audio pipeline during the transfer. **Correction to earlier statement**: the WT32-ETH01 migration would **not** have fixed this — it doesn't change the Teensy↔ESP32 SPI link at all, only what's beyond the ESP32.

**Fix implemented**: `EspSpiDriver::sendPacketTo()` now uses Teensyduino's DMA-driven async SPI transfer (`SPI.transfer(tx, rx, count, EventResponder)`, confirmed available in the local `framework-arduinoteensy` package) instead of blocking `SPI.transfer(buf, count)`. The call queues the transfer and returns immediately; `EspSpiDriver::update()` (already invoked every loop iteration via `netMgr.update()`, no `main.cpp` wiring needed) polls the `EventResponder` and closes out CS/`endTransaction()` once DMA completes. `_txBuffer` moved from a stack-local array to a persistent class member, since the DMA engine now reads/writes it after `sendPacketTo()` has already returned. Guarded against back-to-back calls (e.g. two frames completing in one drain pass): if a previous transfer hasn't finished, waits briefly (polling, not blocking-by-design) with a 5ms safety-valve abort rather than silently dropping a frame or hanging indefinitely. `pio run -e teensy41` builds clean (RAM1 usage up ~30KB from DMA descriptor allocation, still comfortable headroom). Not yet flashed/tested — this is the most invasive of the attempts so far; watch both the buzz and `[SPI-STATS]`/reliability counters closely.

**Retest result**: async DMA send confirmed working as designed — measured audio-send latency dropped from ~715µs to ~302µs (the remainder is the two `delayMicroseconds()` pre-transfer pads, not the actual transfer, which now happens off-CPU). Buzz still present, seemingly unchanged in character. This is an important negative result: a ~300µs stall producing the same buzz as a ~700-1400µs one doesn't fit a simple "blocking duration" model well.

**Gap found**: every attempt so far only touched the *send* path (`sendPacketTo()`). `EspSpiDriver::parsePacket()` — the *receive* path, polled every loop iteration via `VoterClient::update()` — was completely untouched and had zero instrumentation. Worse, its "idle status" branch (READY went high but nothing meaningful was actually queued by read time) was unconditionally clocking out a full padded-to-512-byte dummy transfer — **~2ms at 2MHz, ~10% of the entire 20ms audio budget, in one blocking call, for no reason** — every time this fired. No visibility existed into how often it fires (any real server traffic back to this client - pings, timing packets, other repeaters' voted audio - or even a stale/racy READY trigger would hit this).

**Fix implemented, then reverted (regression found)**: removed the padding entirely from all three branches of `parsePacket()`, matching the send-path right-sizing reasoning. **Broke Voter auth on real hardware** — the run never got past "Host Password Accepted" despite `[RX-STATS]` showing `parsePacket()` firing normally (3-4 calls/5s). Root cause, most likely: right-sizing the *send* path (master chooses to transmit less) has been proven safe across many runs, but this was a different direction — the master ending its *read* early. The ESP32 side's `t.length` is still configured for the full `MAX_SPI_BUF*8` bits per queued transaction; its newly-async `spi_slave_queue_trans()`/`get_trans_result()` pipeline (added earlier in Phase 0) most likely doesn't cleanly handle CS-driven early termination the way the old blocking `spi_slave_transmit()` might have, leaving the next queued transaction desynced — which would explain subsequent auth responses silently failing to relay. **Reverted**: padding restored on all three branches; the (safe, valuable) `[RX-STATS]` instrumentation (`_rxCallCount`/`_rxTotalUs`) was kept. Confirmed builds clean. Right-sizing this path is possible in principle but needs a coordinated ESP32-side change (matching `t.length`/queueing to a shorter expected length) designed and tested together, not a master-side-only change again.

**Status**: SPI throughput (Phase 0's actual goal) independently confirmed solid regardless of the buzz investigation — 50pps sustained, ~715µs latency (send-path, pre-async-fix baseline), `over15ms=0`. The `[RX-STATS]` instrumentation is live and safe to use for diagnosing how often/how long the receive path blocks, even though right-sizing it is on hold. Buzz investigation is unresolved as of this entry — next retest should re-check both the buzz and auth together now that the regression is fixed.

**Second regression found (same async-send change), fixed**: user noticed syslog messages arriving over the WiFi/SPI path with their tail corrupted — e.g. `"Boot Comple\0\0"`, `"...40:16\0\0"` (rsyslog renders embedded NUL as `#000`) — consistently the *last two bytes* replaced with zeros regardless of message length, not simple truncation. Root cause: `sendPacketTo()`'s async DMA call used `_txBuffer` as **both** the TX and RX buffer (`SPI.transfer(_txBuffer, _txBuffer, ...)`). That's safe for the old blocking in-place transfer (one byte fully completes before the next starts), but with separate DMA channels for TX and RX running concurrently, the RX channel writing incoming (mostly-zero, since the ESP32 has little to send back on an outbound-only call) bytes into a *shared* buffer could race ahead of the TX channel finishing that same address, clobbering the tail of the outgoing message with zeros just before it went out. **Fixed**: added a separate scratch buffer for the async transfer's incoming side — the two DMA channels no longer touch the same memory, eliminating the race.

**Retest result**: auth and syslog both confirmed fixed. `[RX-STATS]` revealed the real remaining lead: `parsePacket()` (the receive path, still fully blocking/un-asyncified at this point) was firing 4-6 times/5s at **~2.7ms per call** — by far the largest single blocking stall in the whole system, previously invisible, present the entire time every send-side fix was being tried.

**Major fix implemented**: made the receive path async too, using the same DMA/`EventResponder` pattern as the send path, but this time **without** shrinking the transfer length (that's what broke auth last time) — only removing the CPU-blocking wait. This required unifying send and receive under one shared in-flight state (`SpiTxnType::NONE/SEND/RECEIVE` in `include/EspSpiDriver.h`) since both directions share the same physical bus/CS line and can't run concurrently even though both are now non-blocking: `update()` now polls for a completed transaction first (`_pollAsyncTxn()`), then opportunistically starts an async receive if READY is high and nothing's in flight (`_startAsyncReceiveIfNeeded()`); `sendPacketTo()` waits for any in-flight transaction (either direction) to clear before queueing a new one, same bounded-wait-with-safety-valve pattern as before. Learned from the first async bug and used dedicated separate TX/RX scratch buffers for the receive direction too (`_rxTxDummy`/`_rxAsyncBuffer`), not shared. `sendPacketTo()`'s READY-high fallback to a full-size transfer was removed as no longer needed — receiving is now handled entirely independently, not coupled to sends the way the old single-transaction-does-both design required.

**Bug caught in self-review before this even reached hardware**: `resolveHostname()` and `getLocalIP()` both loop on `digitalRead(_ready)`, calling `parsePacket()` expecting it to actually drain pending data via a real transaction. Since `parsePacket()` is now just a getter (`return _rxLen;`, no bus activity), those loops would have spun forever waiting for READY to go low with nothing left to clear it — a real hang risk on every DNS lookup / IP query. Fixed with a new `_drainOnePendingBlocking()` helper.

**Retest result: reverted.** Buzz unchanged, and a new regression appeared: `[SPI-STATS]` showed entire 5-second windows with zero audio sends (`82, 93, 0, 0, 170, 250, 250, 192, 0, 0` across consecutive windows) — never seen in any earlier test, most likely send/receive contending over the shared bus/CS line in a way that occasionally stalled audio outright. On top of that, `[RX-STATS] avgUs` didn't even drop from making the path async (~2734µs, same as the blocking version) — the change wasn't delivering its intended benefit either. ## Buzz: root cause found via systematic A/B bisection

At the user's suggestion, stopped guessing and bisected properly against a known-good reference point.

**Step 0 — full pre-Phase-0 revert (`git stash`).** Flashed the exact original code (both boards) plus only the one unrelated `soc/gpio_struct.h` toolchain-compat include. Result: **no buzz.** Conclusively rules out wiring/grounding/hardware and confirms this is a firmware regression introduced somewhere in Phase 0 — the "wiring test" comparison against Ethernet earlier couldn't actually distinguish this, since it was confounded with too many simultaneous differences.

**Step 1 — restore Phase 0, revert only the ESP32-side blocking-vs-async change** (`spi_slave_queue_trans`/`get_trans_result` → back to blocking `spi_slave_transmit()`), Teensy side untouched. Result: **buzz still present.** Rules out the ESP32 pipelining entirely.

**Step 2 — also revert the Teensy-side send to blocking** (removed the DMA/`EventResponder` mechanism), keeping right-sized length/200µs delay/2MHz clock. Result: **buzz still present.** Rules out DMA/async on both sides of the link entirely — this invalidates the original "CPU-blocking-disrupts-audio-ISR" theory the whole investigation started from.

**Step 3 — revert only the transfer length** (back to full `MAX_SPI_BUF`, zero-padded, instead of right-sized ~194 bytes), keeping blocking transfer, 200µs delay, 2MHz clock. Result: **no buzz.**

**Root cause confirmed: transfer-length right-sizing.** Best explanation: the original full-length transfer is mostly zero-padding after the real ~194-byte payload — MOSI sits idle (constant, non-toggling) for most of the transfer while only SCLK keeps ticking. Right-sizing eliminated that idle tail, so every byte of the (shorter) transfer is real, actively-toggling data — apparently higher bit-transition density despite the shorter total duration, which is what coupled audibly into the audio path. Not blocking vs. async, not the ESP32, not the delay pad, not the clock speed — all four of those were tried and ruled out. Given the enormous timing headroom (even a full 512-byte transfer at 2MHz is only ~2ms against the 20ms budget), reverting the length costs nothing functionally.

**Final fix**: restored async DMA send on the Teensy (confirmed innocent, real benefit: CPU free during the transfer) and async pipelining on the ESP32 (confirmed innocent, real benefit: doesn't block webServer/heartbeat), kept the 200µs delay and 2MHz clock (both confirmed innocent), but transfer length is back to the full `MAX_SPI_BUF` unconditionally — no more right-sizing, no more READY-high special case for transfer length (moot now that every transfer is full-length), though the real `parsePacket()`-based collision-evasion drain stays (still needed for correctness: the async send's own RX side is discarded/never parsed, so without an explicit drain, pending inbound data would never reach `_handlePacket()` even though it's electrically clocked out cleanly). Both `pio run -e teensy41` and `pio run -e esp32` build clean.

## Phase 2 — ESP32 Firmware Update via Teensy

Since the Teensy is the only physical/USB interface for the whole unit, the ESP32 gets updated by the Teensy, not by plugging into it directly — important once units are deployed with WT32-ETH01's awkward flash-mode entry (no boot button, GPIO0 tied up by the ETH clock, per Phase 1). Teensy firmware releases going forward bundle a versioned ESP32 firmware image; on boot/reconnect the Teensy checks the ESP32's running version and pushes an update if it's behind. **Buildable and testable on the current ESP32-WROOM devkit, independent of Phase 1.**

- **Storage**: no external flash chip exists on this board (checked `docs/wiring_pin_table.csv` — nothing wired for one, and no `LittleFS`/`SerialFlash` usage exists in the codebase today). Store the ESP32 `.bin` on the Teensy's own onboard QSPI program-flash via `LittleFS_QSPIFlash` (bundled with Teensysduino, no extra hardware) — current build uses `code:301160 + data:109008 + headers:9128` bytes, leaving **~7.7MB free** (`teensy_size` output, confirmed this session). A WT32-ETH01 Arduino build (WebServer + ETH + SPI-slave, no WiFi/BLE) realistically compiles to ~700KB–1.3MB — comfortable margin even doubled up for a rollback copy. `SerialFlash` (which does assume an external chip) is not the right library here — don't use it. Pair the stored blob with a version constant compiled into the Teensy firmware.
- **New SPI commands** (append to `SpiProtocol.h`, same style as existing `CMD_*`): `CMD_GET_FW_VERSION` (ESP32 reports its running version), `CMD_OTA_BEGIN` (announce incoming blob + size + checksum), `CMD_OTA_CHUNK` (payload chunk, reuses the existing 512-byte transaction framing), `CMD_OTA_END` (finalize + reboot).
- **ESP32 side**: on `CMD_OTA_BEGIN`, call `Update.begin(size)`; on each `CMD_OTA_CHUNK`, `Update.write(buf, len)`; on `CMD_OTA_END`, verify the checksum, `Update.end()`, `ESP.restart()`. This writes to the inactive OTA partition — if the new image fails validation, the ESP32's existing bootloader behavior keeps the old partition bootable, so a failed transfer doesn't brick the board (confirm this fallback behavior during implementation, don't assume without testing).
- **Version check**: Teensy requests the ESP32's version once per boot (or on reconnect after a link drop); if `esp32_reported_version < bundled_version`, kick off the OTA sequence before resuming normal traffic. Guard against update-loops (e.g. a bad bundled image that never reports the expected version back) with a retry cap and a clear serial/log error rather than an infinite retry cycle.
- **Scope note**: this is genuinely new infrastructure, not a refactor of anything existing — treat it as its own testable unit (can be built and proven on the current devkit ESP32 before or independent of the Phase 1 board swap, similar to Phase 0).

## Deferred — Syslog Redesign (not designed in this plan)

Flagging, not designing: syslog reportedly didn't work reliably over the SPI/WiFi-fallback path previously — a distinct problem from the audio-pps loss (Phase 0.2 item #6's `Logger::update()` bounded-drain fix is a stopgap for the blocking-multiple-sends hazard, not a full fix).
